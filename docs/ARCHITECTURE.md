# Архитектура проекта (черновик v0.1)

Рабочее название: **Spicy-hemp**. Ручные горшки с пряными травами. На каждом горшке стоит QR-код, который открывает «паспорт растения» с уходом, характеристиками и связями по семействам. Каждый скан попадает в аналитику.

## 0. Принятые решения (бриф, раунд 1)

| Вопрос | Решение | Последствия |
|---|---|---|
| QR | **Уникальный на каждый горшок** (`/p/{code}`) | Таблицы `batches`/`pots` обязательны уже в MVP, нужен генератор кодов и листов для печати |
| MVP | **Справочник + интернет-магазин** | Магазин входит в первую версию, срок и объём выше, см. раздел 10 |
| Рынок и языки | **Украина + международный, uk и en** | i18n на два языка с первого дня; оплата: LiqPay/Monobank для UA и Stripe для остального мира; доставка Nova Poshta + международная |
| Бренд | **Нейтральное имя и короткий домен**; Spicy-hemp остаётся только названием репозитория | Домен и название выбираем до запуска магазина и платёжек |

### Магазин в MVP: решение по реализации

Горшки ручной работы это маленький каталог и штучный товар, поэтому полноценная платформа вроде Shopify избыточна, а кастомный магазин проще связать с `pots`. Предлагаю:

- Товар = **SKU** (модель горшка + вид растения), а конкретный проданный экземпляр = **`pots`**-запись, закреплённая за заказом при упаковке. Так QR на коробке гарантированно соответствует заказанному виду.
- Таблицы: `products`, `product_variants`, `inventory`, `carts`, `orders`, `order_items`, `payments`, `shipments`.
- Оплата: Stripe Checkout (международные) и LiqPay/Monobank (UA), webhooks → `payments`. Карточные данные у нас не хранятся.
- Складской учёт простой: `inventory` по SKU, резерв на время оплаты.
- Налоги/ФОП, возвраты и гарантия «растение живёт» нужно будет продумать юридически (см. вопросы).

## 1. Цели

| Цель | Метрика успеха |
|---|---|
| Покупатель за 1 скан получает всё про своё растение | Скан → страница < 1 с на мобильном, bounce < 40% |
| Растения живут дольше, поэтому покупатели возвращаются и рекомендуют | Повторные сканы на горшок, доля возвращающихся |
| Понимать, какие виды и партии «заходят» | Сканы по видам/партиям/регионам, конверсия скан → покупка |
| Контентом управляет один человек без разработчика | Правка в Notion появляется на сайте < 5 мин |
| QR никогда не «умирает» | Динамические короткие ссылки: цель меняется без перепечатки |

## 2. Стек

| Слой | Выбор | Почему |
|---|---|---|
| Фронтенд | **Next.js (App Router) + TypeScript + Tailwind** | ISR/статика для страниц растений, SEO, один код для сайта и кабинета |
| Хостинг | **Vercel** (или Cloudflare Pages) | Edge-функции для редиректа QR, ISR из коробки, гео-заголовки |
| База | **Supabase (Postgres)** | Данные, Auth, Storage, RLS, Edge Functions, cron в одном месте |
| CMS | **Notion** | Редакторский интерфейс, база знаний, связи между таблицами |
| Аналитика событий | **Своя таблица `scan_events` в Supabase** + (опционально) **PostHog** | Скан привязан к конкретному горшку и партии, этого нет в готовых счётчиках |
| Веб-аналитика | **Plausible/Umami** (без cookies) | Поведение на сайте без GDPR-баннера |
| Платежи (MVP) | **Stripe** (международные) + **LiqPay или Monobank Acquiring** (UA) | Оба рынка с первого дня |
| E-mail | **Resend** | Напоминания и транзакционные письма |
| Мониторинг | **Sentry + Vercel Analytics** | Ошибки и скорость |
| CI | **GitHub Actions** | lint, typecheck, миграции, превью-деплой |

## 3. Потоки данных

```
 Notion (редакция)                 Supabase (источник правды для сайта)           Посетитель
 ┌───────────────┐   webhook/cron  ┌───────────────────────────────┐
 │ Species       │ ───────────────▶│ sync worker (Edge Function)   │
 │ Families      │   Notion API    │  - Notion → нормализация      │
 │ Care topics   │                 │  - картинки → Storage         │
 │ Pests/Disease │                 │  - upsert в Postgres          │
 │ Recipes/Uses  │                 └──────────────┬────────────────┘
 │ Glossary      │                                │ revalidate (ISR tag)
 └───────────────┘                                ▼
                                       Next.js (Vercel)  ◀── 302 ── /p/{code} (Edge)  ◀── скан QR
                                       /plants/{slug}                    │ пишет scan_event
                                       /families/{slug}                  ▼
                                       /account (фаза 2)           scan_events (Postgres)
```

Ключевые решения:

1. **Notion это редакторская среда, не рантайм.** Сайт никогда не ходит в Notion при запросе (лимит ~3 запроса/с, медленно, ссылки на файлы живут около часа). Контент синхронизируется в Supabase, страницы строятся из Postgres.
2. **Картинки из Notion копируются в Supabase Storage** при синхронизации и отдаются через CDN (Next/Image).
3. **Синхронизация:** Notion webhook → Edge Function → upsert → `revalidateTag`. Резервный cron раз в 15 минут сравнивает `last_edited_time`. Публикуются только записи со `Status = Published`.
4. **Динамический QR:** на горшке код вида `https://<короткий-домен>/p/{pot_code}`. Edge-обработчик записывает скан и делает 302 на страницу вида. Цель можно менять без перепечатки.

## 4. QR и идентичность горшка

- **Уровень A (старт):** один код на вид: `/s/{species_code}`. Дёшево, но аналитика только по видам.
- **Уровень B (рекомендую):** уникальный код на каждый горшок: `/p/{pot_code}`, например `K7M2QX`. Это 6–8 символов base32 без похожих `0/O/1/I`, плюс контрольный символ. Даёт партию, дату посадки, «паспорт горшка», историю и привязку к владельцу. Аналитика по партиям и каналам продаж.
- Печать: QR уровня M, quiet zone 4 модуля, минимум 20×20 мм, высокий контраст. Для влажной среды лучше гравировка/выжигание или влагостойкая плёнка; нужен тест на полив и свет.
- Рядом с QR короткий URL текстом (если скан не сработает).
- Ссылка с горшка ведёт на **страницу растения в контексте горшка**: «Ваш базилик из партии №12, посажен 14 сентября».

## 5. Модель данных (Supabase / Postgres)

**Контент (синхронизируется из Notion, только чтение для клиента):**

- `families` (id, notion_id, slug, name_i18n, description_i18n, cover)
- `species` (id, notion_id, slug, family_id, latin_name, names_i18n, summary_i18n, difficulty, light, water_freq, humidity, temp_min/max, soil, pot_size, edible, pet_safe, harvest_tips, propagation, seasonality, cover, status, updated_at)
- `care_sections` (species_id, kind: light|water|feeding|pruning|harvest|winter|problems, body_md_i18n, sort)
- `pests_diseases` и связь `species_pests`
- `uses` (кулинария, чаи, применение) и связь `species_uses`
- `species_related` (species_id, related_id, relation: same_family|companion|substitute)
- `glossary`
- `content_sync_log` (run_id, source, status, changed, error)

**Операционка:**

- `batches` (id, code, made_on, notes, potter, clay_type, glaze)
- `pots` (id, code, batch_id, species_id, planted_on, status: made|planted|sold|returned, sold_channel, sold_on)
- `scan_events` (id, ts, pot_id nullable, species_id, country, region, city, device, os, referrer, utm_*, visitor_hash, is_first_scan)
- Агрегаты: materialized view `scan_daily` (дата × вид × партия × страна)

**Пользователи (фаза 2):** `profiles`, `user_plants` (привязка горшка к аккаунту), `reminders`, `care_logs`, `photos`.

**Магазин (фаза 3, если нужен):** `products`, `orders`, `order_items`, `customers`.

**Безопасность:** RLS включён на всех таблицах. `anon` читает только опубликованный контент. `scan_events` пишутся только через серверный код (service role). Пользователь видит только свои `user_plants`/`reminders`. Секреты только на сервере.

## 6. Структура Notion

Одна рабочая область, базы данных со связями (Relation):

| База | Ключевые свойства |
|---|---|
| **Species** | Slug, Latin name, Name RU/UK/EN, Family (relation), Difficulty, Light, Water, Humidity, Temp, Soil, Edible, Pet-safe, Status (Draft/Review/Published), Cover, страница с разделами ухода |
| **Families** | Slug, Name i18n, описание, Species (rollup) |
| **Pests & Diseases** | Симптомы, лечение, профилактика, Species (relation) |
| **Uses** | Тип (кухня/чай/ароматерапия), рецепт, Species |
| **Glossary** | Термин, определение |
| **Batches / Pots** | При желании ведутся тут, но источником правды остаётся Supabase |

Страница вида строится по **шаблону**: одинаковые заголовки (Свет, Полив, Подкормка, Обрезка, Сбор урожая, Зимовка, Проблемы). Так синхронизация превращает их в `care_sections`. Статус `Review → Published` служит редакторским флагом.

## 7. Страницы и поведение сайта

- `/p/{code}`: Edge-редирект + логирование скана. Показывает контекст горшка.
- `/plants/{slug}`: паспорт вида: быстрая карточка (свет/вода/сложность), «ключевые правила», разделы ухода, проблемы, применение, «похожие» и «семейство».
- `/families/{slug}`: семейство и все его виды.
- `/plants`: каталог с фильтрами (свет, съедобное, безопасно для животных).
- `/about`, `/care-basics`, `/glossary`.
- Фаза 2: `/account` (мои растения, напоминания о поливе, журнал, фото).
- Фаза 3: `/shop`, корзина, оплата.
- Технически: PWA (офлайн-кэш последних страниц), JSON-LD (`Plant`, `HowTo`, `FAQPage`), i18n (ru/uk/en), `sitemap.xml`.

## 8. Аналитика

События: `scan`, `view_section`, `outbound_click` (семейство/статья), `cta_click` (купить ещё/подписка), `reminder_opt_in`.

Вопросы бизнеса: топ видов по сканам; конверсия скан→повторный скан; сканы по партиям и каналам продаж; география; «мёртвые» горшки (проданы, но ни разу не сканированы); какие разделы читают чаще всего (потому там и нужно улучшать контент).

Приватность: IP не хранится. Гео берётся из edge-заголовков. `visitor_hash = hash(ip + ua + дневная соль)`, cookies для аналитики не нужны.

Дашборд: Supabase + Metabase/Evidence или встроенная страница `/admin/analytics`.

## 11. Риски

1. **Название «hemp»:** платёжные системы, рекламные кабинеты и маркетплейсы могут отклонять. Лучше нейтральное бренд-имя и домен.
2. **QR на керамике:** влажность, глазурь, царапины. Нужен физический тест перед тиражом.
3. **Контент как узкое место:** 20 качественных видов важнее, чем 200 пустых. Нужен шаблон и чек-лист качества.
4. **Notion как зависимость:** кэш в Supabase страхует от его падений и смены лимитов.
5. **Достоверность советов:** на медицинские/пищевые утверждения нужны источники и оговорки (безопасность для животных и детей).

## 12. Открытые вопросы (бриф, раунд 2)

1. **Юридически:** ФОП/ТОВ, группа единого налога, РРО/чеки, доставка за границу, возвраты живых растений.
2. **Доставка:** только Nova Poshta или ещё международная (какие страны)? Упаковка живых растений.
3. **Ассортимент:** сколько SKU на запуске; можно ли выбирать вид растения для горшка; наборы.
4. **Производство:** сколько горшков в месяц, партиями или под заказ (влияет на склад и сроки).
5. **Контент:** кто пишет описания видов, нужны ли источники, перевод на en вручную или AI с проверкой.
6. **Аккаунты:** гостевой checkout достаточен для MVP? (рекомендую да)
7. **Дизайн:** есть ли фирменный стиль, референсы, tone of voice.
8. **Аналитика:** какие отчёты нужны в первый день.
9. **Стек «Декуба»:** если нужно строго повторить, пришли репозиторий или описание.
10. **Бюджет и инфраструктура:** допустимые расходы в месяц (Vercel Pro, Supabase Pro, Notion, домен).
